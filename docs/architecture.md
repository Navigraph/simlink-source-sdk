# Architecture

How the SDK is put together, from the protocol manifest to the C++ and C# packages. For why it's built this way, see
[overview.md](overview.md); for working on it, see [development.md](development.md).

## Layout

```
protocol/source-schema.json        Simlink's source manifest, synced from the Simlink repository
crates/
  simlink-source-sdk-macros/       protocol!(): the manifest as Rust types and Source methods
  socket-io/                       the Socket.IO client: one namespace, JSON, reconnection
  simlink-source-sdk/
    src/
      lib.rs                       UniFFI setup; expands protocol!()
      source.rs                    Source, its lifecycle, errors, listeners
      worker.rs                    the SDK thread: join, emit, answer, reconnect
      discovery.rs                 loopback port probing and mDNS
      logging.rs                   `log` records to a foreign listener
    tests/                         schema, connection and example tests, and a fake Simlink
    examples/                      Rust examples
bindings/
  cpp/                             CMake project over the generated C++ (development)
  cpp/prebuilt/                    CMake project and VS property sheet shipped in the C++ archive
  csharp/                          the NuGet project over the generated C#
examples/cpp, examples/csharp      the same examples in each language
xtask/                             build, bindings, examples, README snippets and packaging
```

## From manifest to packages

```
protocol/source-schema.json
  └─ protocol!()                       Rust types, Event, typed Source methods, connection constants
       └─ simlink-source-sdk           the core, every exported item annotated for UniFFI
            ├─ cdylib  ─ uniffi-bindgen-cs   →  target/bindings/csharp  →  NuGet package
            └─ cdylib  ─ uniffi-bindgen-cpp  →  target/bindings/cpp     →  C++ archive (with the staticlib)
```

- **Bindings are generated, never checked in.** `cargo xtask build` builds the library and runs both generators in
  UniFFI's library mode, which reads the exported API from the compiled dynamic library. Because of
  this, the items `protocol!` generates get bindings like any other UniFFI item.
- **Generators are pinned** in `xtask/src/generators.rs`, each to the commit of a release targeting the workspace's UniFFI minor
  version, and installed into `target/tools` on first use. C# uses [our fork](https://github.com/Navigraph/uniffi-bindgen-cs)
  until upstream merges our fixes.
- **C++ links the static library; C# loads the dynamic one.** The crate builds `lib`, `cdylib` and `staticlib` for
  that reason.

## The protocol macro

`protocol!("../../protocol/source-schema.json")` reads the manifest at compile time and emits:

- **Types** for `SourceOptions`, `HandshakeError`, every event payload, and every command input, output and refusal,
  generated by [typify](https://github.com/oxidecomputer/typify) and annotated as UniFFI records and enums. Each takes
  its name from the schema's `title` (`TelemetryOwnshipEvent`, `AtisGetCommandInput`) or its `$defs` key
  (`FlightPlan`). Only the `$defs` these refer to become types; arrays and maps stay `Vec<T>` and `HashMap<String, T>`.
- **Wire types** only the core reads, `SourceCapabilities` and `SourceErrorFrame`, generated the same way into a
  private `wire` module. The core builds and parses these frames with serde, so a manifest change to them fails to
  compile rather than misbehave.
- **`Event`**, one variant per event channel, and an `emit_<event>` method on `Source` for each.
- **Per command**: a `<Command>Handler` foreign trait, a `<Command>Reply` object with `ok` and `refuse`, and an
  `on_<command>` method on `Source` to register the handler.
- **`Channel`**, every event and command, for rejections, with an `Other` variant for what a newer Simlink sends and
  `wire_name` for the name Simlink sends.
- **Connection constants**: protocol version, namespace, default port and probe limit, mDNS service type, error
  channel, Socket.IO path and message size limit, and the rate limit per event.

In `crates/simlink-source-sdk-macros/src`, `manifest.rs` reads the manifest into a model and checks it, and
`types.rs`, `api.rs` and `consts.rs` each generate their part of the output from that model.

Before handing schemas to typify, the macro strips what Simlink validates anyway (`minLength`, `pattern`, `format`,
defaults, and `const` properties with a default). Otherwise typify would turn them into validating newtypes or fields
integrators must fill in. Channel descriptions and deprecations carry over as doc comments and `#[deprecated]`. Every generated enum is
`#[non_exhaustive]`, so a manifest update that adds a variant doesn't break integrators' Rust `match`es.

The macro fails the build when the manifest has something the SDK doesn't handle: a key it neither reads nor ignores
on purpose, or a channel that doesn't originate from the source. `manifest.rs` reads the manifest into serde structs,
`serde_ignored` reports any key they don't read, and the ones ignored on purpose are fields typed `Ignored`, with the
reason. `include_bytes!` on the manifest rebuilds the crate whenever it changes.

## The core

### Source

A `Source` is configured, then started:

1. `Source::new(options, events)` takes the source's identity and the events it will emit.
2. `on_<command>`, `on_state` and `on_rejected` register handlers and listeners. Commands are declared by
   registering their handler.
3. `start` builds the handshake descriptor (options plus declared capabilities) and hands everything to a worker
   thread. Registering after `start`, or emitting before it, fails with `WrongState`.

Dropping the `Source` stops the thread and leaves Simlink. Handlers and listeners must not hold their `Source`, or it
never drops.

### The worker thread

Each started source runs one thread (`worker.rs`, named `simlink-source`). The public API only sends it messages over
a channel and wakes it, so emitting never blocks on the network. Otherwise the thread sleeps until the socket needs it
or an emit or rejoin is due.

- **Finding Simlink.** It probes Simlink's default port and the next few on loopback first, then browses mDNS for
  instances on other machines that advertise a matching protocol major. Addresses that don't take a quick TCP connect are
  skipped, so a closed port or stale record doesn't cost a full handshake timeout. It joins through the first that
  accepts the handshake.
- **Reconnecting.** The Socket.IO client reconnects on its own, with backoff from 1 to 10 seconds. A refusal or a
  server disconnect ends the namespace, so the thread joins again after its own backoff over the same range, which
  starts over once a connection has lasted 10 seconds. A `HANDSHAKE_IDENTIFICATION_INVALID` refusal stops the source,
  since retrying would fail the same way.
- **Emitting.** Only the latest payload per event is kept and sent no faster than the event's rate limit, so a
  source can emit every frame without flooding Simlink. While the socket is backlogged, newer payloads replace
  queued ones. Payloads over Simlink's message limit are refused up front, since
  Simlink would drop the connection. Emits while disconnected are dropped.
- **Commands.** Simlink sends commands as events awaiting an ack. The thread hands each to its handler with a reply
  that can be answered later from any thread, at most once. Each connection is numbered, so a reply to a command
  from a previous connection is dropped, so it can't answer a different request.
- **Rejections.** Frames on Simlink's error channel go to the rejection listener, with each issue's path formatted
  like `aircraft.position.latitude` or `[3].key`.

### The Socket.IO client

`crates/socket-io` is a Socket.IO v5 client over Engine.IO v4, websocket transport only, joined to one namespace.
It's ours because no Rust client answers server-initiated acks, which is how Simlink sends commands. It knows nothing
about Simlink; the core passes it the path, namespace, handshake payload and addresses to try.

It follows the [Socket.IO](https://github.com/socketio/socket.io-protocol) and
[Engine.IO](https://github.com/socketio/engine.io-protocol) specs, and the reference client, socket.io-client, where
they leave behavior open, as with reconnection. Every frame a server can send is either decoded or closes the
connection, so a server can't put the client in a state it doesn't know.

Not implemented, since Simlink doesn't need it:

- **HTTP long-polling**, and so upgrades. Sessions are websocket from the start, which the Engine.IO spec allows.
- **TLS** (`wss://`), query parameters and extra headers.
- **More than one namespace** per connection. Packets for other namespaces are ignored.
- **Acks for events the client sends.** Events go out like the reference client's volatile ones, so a backlogged
  connection drops them.
- **Sending binary.** Binary packets from the server are validated and dropped.
- **Connection state recovery**, which Simlink doesn't enable.
- **Older servers.** A Socket.IO v2 server's connect answer is reported as unsupported.

`Client` runs on the caller's thread: `poll` reads, answers pings, opens and reconnects one step at a time, so the
SDK thread stays responsive.

- After the websocket upgrade the socket is non-blocking, since Windows sockets are unreliable once a read times out.
  Between steps, `poll` sleeps on the OS's readiness API (epoll, kqueue or IOCP, through the `polling` crate) until
  the socket is ready, a deadline such as the ping timeout or backoff passes, or another thread calls its `Waker`.
  An idle source doesn't wake up.
- A server that sends no ping within `pingInterval + pingTimeout` counts as lost, whatever else it sends.
- Acks are sent over the current connection, even for an event from an earlier one, as the reference client does.
  `Client::is_current` tells the caller which, since ack ids start over with each connection.
- `tests/protocol.rs` ports the official protocol test suites to the client's side, and `tests/client.rs` checks the
  reference client's behavior.

### Foreign code

Handlers and listeners are implemented in C++, C# or Rust and called on the SDK's thread, so they should return
quickly. Each call is shielded: a panic, or a foreign exception that arrives as one, is logged and the thread carries
on. The log listener is called from whichever thread logs.

## Packaging

`cargo xtask package` builds release archives into `target/package` and tests each by building its own examples from
the staged copy:

- **C++** (`package cpp`, per platform): the generated headers, the C++ half of the bindings as source, the static
  Rust library, `bindings/cpp/prebuilt/CMakeLists.txt`, the Visual Studio property sheet on Windows, and the examples.
  The user's build compiles the bindings, so they match its compiler and configuration; only the Rust library, whose
  interface is C, is prebuilt. macOS ships one universal library.
- **C#** (`package csharp-runtime` per platform, then `package csharp --runtimes` once): one NuGet package with
  every platform's library under `runtimes/<rid>/native`, targeting .NET Standard 2.0. `bindings/csharp/Polyfills.cs`
  supplies the compiler types the generated code needs that .NET Standard 2.0 lacks.
